# fc-dioxus design

A Dioxus component library over future-css, in the spirit of `dioxus-bulma`: every
CSS component becomes a typed Rust component, every modifier becomes an enum variant or
a field, and every behaviour the TypeScript bindings provide is reimplemented as Rust
event handling over the same pure models the WASM layer already uses.

This document is the architecture. [COMPONENTS.md](COMPONENTS.md) is the per-component
API, [ACCESSIBILITY.md](ACCESSIBILITY.md) is the enforcement and compliance tooling, and
[PLAN.md](PLAN.md) is the order the work happens in.

## Initial implementation notes

The architecture below remains the target. The initial implemented slice is listed
in [PLAN.md](PLAN.md); signatures not exported by the crate remain proposals.

- Dioxus is exactly 0.7.9, with 0.7-compatible transitive crates locked in
  `Cargo.lock`. The verified workspace MSRV is 1.88 because the resolved
  `const-serialize-macro` uses let chains; see [DEPENDENCIES.md](DEPENDENCIES.md).
- All eight upstream models are library dependencies and reexported through
  `fc_dioxus::models`. Upstream PR #44 is merged and pinned, so their default
  `bindgen` feature can be disabled. `cargo xtask models` verifies their dependency
  graphs and native/wasm32 compatibility. Explicit `web-sys/Location` is needed by
  the minimal web dependency graph. No model logic has been copied here.
- `upstream.toml` is the source pin. Sync generates assets, asset constants, token
  data, the marked model dependency block in `fc-dioxus/Cargo.toml`, and a
  checksummed manifest. The gate rebuilds the upstream CSS and compares
  every generated byte, including extra/missing files; fast tests verify the manifest.
- `fc_modifier!` takes the identifier of the single `Bem` constant, rather than
  repeating its string. `Modifier::ALL` and `Modifier::BEM` expose coverage metadata.
- Accessible names use fallible conversion for both literals and runtime strings.
  This resolves the design's proposed debug assertion in favor of the stronger
  no-panics invariant. `FcData` replaces free-form kind/ID strings with `Kind`/`Id`.
- Dioxus 0.7 RSX requires named attributes before spread attributes. `Divider`
  therefore assembles one attribute vector: consumer additions first, component
  class and semantics last, with conflicting semantic fields removed.
- `DomBridge` methods are asynchronous so eval hosts can acknowledge errors.
  All scripts are fixed, all data is sent through the eval channel, and unsupported
  hosts return errors. Only the demo's copy-source action currently uses the bridge;
  overlay behavior and its fallback components are still planned.
- Standalone web reads fixture query inputs before rendering. SSR exports accept
  the same explicit inputs. Fullstack starts with identical default inputs on both
  server and client; request-aware fixture routing and hydration tests are pending.
- Generated tokens currently expose the values upstream's token JSON provides:
  light and dark. High-contrast and brand overrides remain in upstream CSS; a typed
  contrast-pair export is still planned, not synthesized locally.

## Goals

1. **Full coverage.** Every component file in `src/css/components/`, every layout
   primitive, type role, and utility in `src/css/` has a Rust API, and every modifier,
   element, and state attribute in those files is reachable from it. Coverage is
   checked by a test, not by reading this document (see [Coverage is a test](#coverage-is-a-test)).
2. **The CSS stays the source of truth.** The Rust layer emits the markup the CSS
   expects. It never restyles, never adds a class the CSS does not define, and never
   ships its own stylesheet.
3. **Accessible by construction.** An inaccessible use is a compile error where the
   type system can express it, a debug-build report where it cannot, and an audit
   failure in CI either way. See [ACCESSIBILITY.md](ACCESSIBILITY.md).
4. **DRY.** A modifier, a state value, a keyboard contract, or a piece of selection
   logic exists once. Components compose shared pieces; they do not each carry a copy.
5. **Idiomatic, safe Rust.** `#![forbid(unsafe_code)]` in every crate. No panics on
   consumer input. Public types implement the standard traits they can. Clippy clean
   at `pedantic`.

## Non-goals

- **Not a port of the TypeScript bindings.** The bindings mutate DOM they did not
  render. In Dioxus the virtual DOM owns the markup, so a second controller would
  fight it. Behaviour is reimplemented as Dioxus state and handlers, sharing the
  *logic* (the Rust models), not the DOM code.
- **Not a new visual language, and not where new components are invented.** No
  component here has an appearance, a class, or a behaviour that future-css does not
  already have. A novel component is filed upstream; see [Upstream first](#upstream-first).

## Repository and upstream

The library is its own repository. future-css (`rexlunae/future-css`) is **upstream**:
it owns the CSS, the tokens, the reference markup in `demo/fixtures.html`, the
TypeScript bindings, and the pure model crates. This repository owns the Rust
components, the accessibility tooling, and the demo.

Everything taken from upstream comes from **one pinned revision**, recorded in
`upstream.toml`:

```toml
[upstream]
repo = "https://github.com/rexlunae/future-css"
rev = "<commit sha>"        # the only place the upstream version is written
css-version = "0.x.y"       # rendered as data-fc-version for diagnosis
```

- **Model crates** are git dependencies at that revision (`fc-select = { git = ...,
  rev = ..., default-features = false }`) until upstream publishes them, then registry
  dependencies at the matching version.
- **CSS assets, `tokens.json`, and `fixtures.html`** are fetched from the same revision
  by `cargo xtask sync-upstream`, which builds upstream's CSS and copies the outputs into
  `crates/fc-dioxus/assets/` and `upstream/`. A test fails when the committed copies
  differ from what that revision produces.
- **Bumping upstream** is one pull request that changes `upstream.toml`, re-runs the
  sync, and fixes whatever the parity and coverage tests report. The models, the CSS,
  and the fixtures cannot come from different upstream versions, because there is only
  one place to write the version.

### Upstream first

**Novel components are designed and built upstream, not here.** A component is novel
when future-css has no CSS for it, or when it needs a class, a modifier, a state value, a
keyboard behaviour, or a piece of pure logic that upstream does not have. For any of
those:

1. **File an issue in `rexlunae/future-css`** describing the need: the use case, the
   proposed markup and classes, every state, the keyboard and screen-reader contract, and
   which Dioxus component is waiting on it. The issue is the design review; upstream's
   AGENTS.md decides how it is built.
2. **Do not ship a local implementation in the meantime.** No stylesheet, no
   component-specific class, no private copy of logic. A stopgap here becomes a fork of
   the design system that nobody maintains, and the coverage test's rule that every
   emitted class exists upstream rejects it anyway.
3. **Track it.** The component goes into `docs/COMPONENTS.md` under *Waiting on
   upstream* with a link to the issue, and into nothing else until upstream ships it.
4. **When upstream releases it,** bump `upstream.toml` and build the wrapper here under
   the normal rules.

The same applies to bugs and gaps found here in existing upstream components: a missing
modifier, a markup bug, an inaccessible fixture, or a model that needs a new function is
an upstream issue (and, where useful, an upstream pull request), never a local patch.

What this repository may add on its own is limited to things that are not components of
the design system: Rust conveniences that **compose existing upstream components using
only their existing classes and behaviours** (a `ConfirmDialog` made of `Dialog`,
`Button`, and `Cluster`), and the Dioxus plumbing in `core` and `behavior` that replicates
behaviour an upstream binding already defines.

## Crates

Three crates make up this repository's workspace, plus the demo application and the
`xtask` build tool. Dependencies point downward only.

```
fc-tokens      generated from dist/tokens.json; token names, values, contrast pairs
    ^
fc-a11y        rule engine and CLI; knows HTML and WCAG, not Dioxus
    ^
fc-dioxus      the components; depends on fc-tokens, the model crates, and
               (dev only) fc-a11y for its tests

fc-demo        the demo application (not published); depends on fc-dioxus

fc-select  fc-context-menu  fc-grid  fc-diff  fc-git  fc-model  fc-rich-text
    ^ upstream crates at the pinned revision, used as plain Rust libraries with their
      wasm-bindgen glue feature-gated off
```

| Crate | Purpose | Depends on Dioxus |
| --- | --- | --- |
| `fc-tokens` | Typed token names (`Token::ColorTextDefault`), the `var()` string for each, light, dark, and high-contrast values, and the contrast pairs. Generated, checked in, drift-tested. | No |
| `fc-a11y` | Accessibility rule engine over an HTML tree, WCAG mapping, reporters (human, JSON, SARIF), the `fc-a11y` CLI, and the manual review ledger. | No |
| `fc-dioxus` | Components, hooks, behaviours, and the debug-build audit hooks. | Yes |

`fc-a11y` deliberately does not depend on Dioxus. A compliance checker that only
works on one framework's output is a framework feature, not a compliance tool; this
one audits any HTML, including upstream's `fixtures.html`, and so also checks the CSS
library's own reference markup. A finding there is filed upstream.

### Reusing the model crates natively

`fc-select`, `fc-context-menu`, `fc-grid`, `fc-diff`, `fc-git`, `fc-model`, and
`fc-rich-text` already hold the pure logic behind the WASM modules: typeahead,
filtering, roving movement, range selection, diffing, status ordering, and UTF-16
text ranges. `fc-dioxus` uses them directly as Rust dependencies. That is the largest
single DRY win available: the same code answers the same question on every path, and
the existing WASM/JS parity tests already pin its behaviour.

One upstream change makes this work, and it is the first upstream issue this project
files. The crates' `#[wasm_bindgen]` glue moves behind a default-on `bindgen` feature,
and `fc-dioxus` depends on them with `default-features = false`. Without the gate, a
Dioxus web build would link every exported JS shim into the application's binary, and a
native build would carry the glue for nothing. Upstream's `build:wasm` keeps the feature
on, so its shipped modules and size report are unchanged. `fc-core`'s panic hook goes
behind the same feature.

The `bare` (`no_std`) feature is never enabled here. Upstream's AGENTS.md describes the
two-panic-handler collision it causes in any build that mixes it with std.

### Where pure logic lives when no crate has it yet

Some binding behaviour exists only in TypeScript today: calendar math
(`datepicker.ts`), sort comparison (`table.ts`), toast queueing (`toast.ts`), Markdown
(`markdown.ts`), and syntax highlighting (`highlight.ts`). The rule:

- **Small and Dioxus-shaped** (toast queue, sort comparator, roving focus): a pure
  module in `fc-dioxus::behavior`, unit-tested in Rust, with a parity test against the
  upstream TypeScript run from this repository's test suite.
- **Substantial and useful to both sides** (calendar, Markdown, highlighting): a new
  pure crate **upstream**, filed and built under [Upstream first](#upstream-first)
  following upstream's Phase A pattern (primitives at the boundary, size budget,
  `bindgen` feature), with its parity test against the TypeScript living beside it. The
  Dioxus component that needs it waits for it. A Rust port with no parity test is two
  implementations that will drift, which upstream's AGENTS.md calls the worst bug this
  system can have.

## The shared building blocks

These are the pieces every component is built from. A component that reimplements one
of them is a review failure.

### Classes: `Bem`, `ClassList`, and `fc_modifier!`

```rust
/// A BEM block. `const` so every component declares its block once, at compile time.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct Bem(&'static str);

impl Bem {
    pub const fn new(block: &'static str) -> Self { Self(block) }
    pub const fn block(self) -> &'static str { self.0 }
    /// `fc-card__header`
    pub fn element(self, element: &str) -> String { /* ... */ }
    /// `fc-card--elevated`, or nothing for a modifier that renders the bare block.
    pub fn modifier<M: Modifier>(self, m: M) -> Option<String> { /* ... */ }
}

/// Implemented by every modifier enum. `None` means "the bare block".
pub trait Modifier: Copy + Eq + Default + core::fmt::Debug {
    fn suffix(self) -> Option<&'static str>;
}

/// Builds a class attribute without allocating per token.
#[derive(Debug, Default, Clone, PartialEq, Eq)]
pub struct ClassList(String);

impl ClassList {
    pub fn new(base: &str) -> Self;
    pub fn with(self, class: impl AsRef<str>) -> Self;
    pub fn with_if(self, cond: bool, class: impl AsRef<str>) -> Self;
    pub fn with_modifier<M: Modifier>(self, bem: Bem, m: M) -> Self;
    /// Consumer classes go last, so they read as additions in devtools.
    pub fn extend(self, extra: Option<&str>) -> Self;
}
```

Every modifier enum is declared through one declarative macro, so the enum, its
`Default`, its `Modifier` impl, `Display`, `FromStr`, and the list of every variant
the coverage test reads all come from a single declaration:

```rust
fc_modifier! {
    /// Emphasis of a button. `Neutral` renders the bare `.fc-btn`.
    pub enum ButtonVariant for "fc-btn" {
        #[default] Neutral => None,
        Primary   => "primary",
        Secondary => "secondary",
        Ghost     => "ghost",
        Subtle    => "subtle",
        Danger    => "danger",
    }
}
```

It is `macro_rules!`, not a procedural macro: a proc-macro crate is a build dependency
with its own compile cost, and nothing here needs one.

**Why per-component enums rather than one shared `Size`.** Sizes differ by component:
buttons have `sm` and `lg`, avatars and spinners `xs` through `xl`, progress only `sm`.
A shared `Size` would let `Button { size: Size::Xl }` compile and silently render the
default. The type should only offer what the CSS defines, so each component declares its
own enum through the macro, and the macro makes that a one-line cost rather than a
duplicated impl.

### The dual-audience contract: `FcData`

Upstream's AGENTS.md defines the `data-fc-*` attributes. One struct renders them, so no
component spells an attribute name by hand:

```rust
#[derive(Debug, Clone, Default, PartialEq)]
pub struct FcData {
    pub kind: Option<&'static str>,   // set by the component, never by the consumer
    pub id: Option<String>,           // mirrors the runtime id
    pub seq: Option<u64>,             // monotonic ordering
    pub role: Option<MessageRole>,
    pub state: Option<Lifecycle>,
    pub ts: Option<Timestamp>,        // epoch ms or validated ISO-8601
    pub truncated: bool,              // set by Clipped<T>, never by hand
}

impl FcData {
    pub fn attributes(&self) -> Vec<Attribute>;
}
```

Components with dynamic data take `id`, `seq`, and `ts` props and fill `kind`, `role`,
`state`, and `truncated` themselves. Styling never reads them (the contract says it must
not), so a component renders correctly with all of them absent.

**Secrets.** `FcData` has no free-form field. The values are an id, an integer, two
enums, a timestamp, and a boolean, so there is nowhere to put a token. Component-specific
attributes (`data-fc-provider`, `data-fc-model`) are typed the same way.

### Shared enums

| Type | Variants | Rendered as |
| --- | --- | --- |
| `Lifecycle` | `Pending`, `Queued`, `Streaming`, `Running`, `Complete`, `Aborted`, `Denied`, `Error` | `data-fc-state` |
| `MessageRole` | `User`, `Assistant`, `System`, `Tool` | `data-fc-role` |
| `Tone` | `Info`, `Success`, `Warning`, `Danger` | `--info` etc. on alert, toast |
| `Orientation` | `Horizontal`, `Vertical` | `aria-orientation` |
| `HeadingLevel` | `H1` to `H6` | the heading element for a component's title |
| `Availability` | `Enabled`, `Disabled`, `Unavailable { reason: Id }` | see below |

Component-specific state sets stay component-specific: git status (`added`, `modified`,
`deleted`, `renamed`, `untracked`, `conflicted`), terminal (`complete`, `disconnected`,
`error`), editor (`saving`, `error`), webview security. Folding them into `Lifecycle`
would let a git row claim it is `streaming`.

**`Availability` encodes the button doc's disabled decision.** The CSS documents two
kinds of unavailable: `disabled` removes the control; `aria-disabled="true"` keeps it
focusable so the reason is discoverable, and is the recommended default. The enum makes
the second kind carry its reason:

```rust
pub enum Availability {
    #[default] Enabled,
    /// Meaningless in this state. Removed from the tab order.
    Disabled,
    /// Unavailable right now. Stays focusable; `reason` is the id of visible text
    /// explaining why, rendered as `aria-describedby`.
    Unavailable { reason: Id },
}
```

`aria-disabled` alone does not stop activation, so every component that accepts
`Availability` also drops its own event handlers while `Unavailable`. That check lives in
one helper, `Availability::guard(handler)`, so no component forgets it.

### Accessible names: `AccessibleName`, `Alt`, `Label`

```rust
/// A non-empty, trimmed name, so a control can never be given the name "".
pub struct AccessibleName(Cow<'static, str>);
/// Runtime text (translations, user data): fails on an empty or whitespace string.
impl TryFrom<String> for AccessibleName { /* ... */ }
/// Literals, so `label: "Close"` works in `rsx!` through `#[props(into)]`. An empty
/// literal is a debug assertion and an `fc-a11y` error rather than a type error,
/// because `From` cannot fail; runtime text has no such path.
impl From<&'static str> for AccessibleName { /* ... */ }

/// Image alternatives. There is no default: the author must choose.
pub enum Alt {
    Text(AccessibleName),
    /// Purely decorative: renders alt="" (images) or aria-hidden="true" (icons).
    Decorative,
}
```

Components whose name cannot come from visible children take a required
`label: AccessibleName` prop. Icon-only buttons are a separate component (`IconButton`)
with a required label rather than a `Button` with an optional `aria_label`, because a
required prop is a compile error when missing and an optional one is a bug report.

### Truncation: `Clipped<T>`

```rust
/// Text that may be shown shortened. Holding the full value is not optional.
pub struct Clipped { full: String, shown: ClipMode }
pub enum ClipMode { Full, Lines(u8), Chars(usize) }
```

A component that shortens text takes `Clipped`, which sets `data-fc-truncated="true"`
whenever the shown text differs from the full text and keeps the full value reachable
(expandable body, or `title` plus an accessible description). No component accepts a
pre-shortened `String` where truncation is possible.

### Controlled and uncontrolled state: `use_controllable`

Every stateful component (open, selected, value, expanded, active cell) supports both
modes with one hook rather than a hand-written pair of code paths each:

```rust
pub fn use_controllable<T: Clone + PartialEq + 'static>(
    value: Option<ReadSignal<T>>,     // controlled when Some
    default: impl FnOnce() -> T,      // initial value when uncontrolled
    on_change: Option<EventHandler<T>>,
) -> Controllable<T>;

impl<T> Controllable<T> {
    pub fn get(&self) -> T;
    /// Requests a change. Uncontrolled: stores and notifies. Controlled: only notifies;
    /// the owner decides.
    pub fn set(&self, next: T);
}
```

Naming is uniform across the library: `value` / `default_value` / `onchange` for values,
`open` / `default_open` / `onopenchange` for disclosure-like state.

### Ids: `use_id`

ARIA relationships (`aria-labelledby`, `aria-describedby`, `aria-controls`,
`aria-activedescendant`) need ids that are unique and that match between server render
and hydration. `use_id()` takes the next value from a counter held in the `FutureCss`
root context, so the same tree yields the same ids on both sides. A consumer-supplied
`id` always wins. Duplicate ids are a debug-build report and an `fc-a11y` error.

### Compound components and context

Components with parts follow the `dioxus-bulma` compound pattern (`Card { CardHeader {}
CardBody {} }`), with convenience props for the common case (`Card { title: "..." }`).
Where parts must coordinate (tabs and their panels, a listbox and its options, a menu and
its items), the parent provides a typed context and the parts read it. Coordination never
goes through the DOM.

### Platform bridge: `DomBridge`

A few behaviours need the host rather than the virtual DOM: `showModal()` and
`close()` on `<dialog>`, `showPopover()` and `hidePopover()`, focusing a specific node,
and `scrollIntoView`. They go through one trait, with an implementation per renderer
family (see [Renderers](#renderers)):

```rust
pub trait DomBridge {
    fn show_modal(&self, id: &Id) -> Result<(), DomError>;
    fn close_dialog(&self, id: &Id) -> Result<(), DomError>;
    fn toggle_popover(&self, id: &Id, open: bool) -> Result<(), DomError>;
    fn focus(&self, id: &Id) -> Result<(), DomError>;
    fn scroll_into_view(&self, id: &Id, block: ScrollBlock) -> Result<(), DomError>;
}
```

- **`web` feature:** `web-sys`, via `MountedData::as_web_event()` and checked
  `dyn_into` casts. No `unsafe`, no `unchecked_into`.
- **Webview and remote renderers (desktop, mobile, liveview):** `document::eval` with a
  fixed script and the id passed as data, never interpolated into the script text.
- **Native (Blitz) and SSR:** a bridge that reports `DomError::Unsupported` for anything
  the host cannot do, so the component takes its documented fallback rather than
  failing.

Focus that Dioxus can do itself (`MountedData::set_focus`) uses Dioxus, not the bridge.
Overlays render the platform elements first (`<dialog>`, `popover`, `<details>`), so with
no script at all, as under SSR before hydration, they still work the way the CSS library's
no-JS fallback documents.

### Styles: one stylesheet per component

```rust
// core/assets.rs, generated by the sync script
pub const BUTTON_CSS: Asset = asset!("/assets/components/button.css");
```

Each component renders `document::Stylesheet { href: BUTTON_CSS }` once (Dioxus
deduplicates by href), and the `FutureCss` root loads the layer order, tokens, reset,
base, layout, type, and utilities. A page therefore downloads only the components it
renders, which is the per-page budget `tests/budget.test.ts` already enforces for the CSS
library. Manganis drops assets that no compiled code references, so unused components cost
nothing.

The CSS files are copied from upstream's build output at the pinned revision into
`crates/fc-dioxus/assets/` by `cargo xtask sync-upstream`, committed (a published crate
must contain its assets), and a test fails when the committed copy differs from what that
revision builds. The copy is never hand-edited; a change to it is an upstream change.

The stylesheet assets opt out of dx's minifier. Upstream writes its glyphs as CSS escapes
(`content: "\2713"`), which read the same under any charset; the minifier decodes them to
raw UTF-8, and a host that serves the CSS into a page it does not decode as UTF-8 then
draws the check mark as `âœ“`. `tests/encoding.rs` holds both halves: the vendored rules
are ASCII, and every stylesheet asset keeps them that way.

Consumers who already load `future-css.css` themselves set `FutureCss { stylesheets:
Stylesheets::External }` and the components emit no stylesheet links.

### Theme

```rust
#[component]
pub fn FutureCss(
    #[props(default)] theme: Theme,           // System, Light, Dark, HighContrastLight, HighContrastDark
    #[props(default)] design: Option<Design>, // data-fc-design: geometry, depth, surface, type
    #[props(default)] palette: Option<Palette>, // data-fc-palette; defaults to design.palette()
    #[props(default)] brand: Option<Brand>,   // data-fc-brand, e.g. Brand::Forest
    #[props(default)] direction: Option<Direction>, // Ltr, Rtl, or inherit
    #[props(default)] stylesheets: Stylesheets,
    children: Element,
) -> Element;

pub fn use_theme() -> ThemeHandle; // read and switch at runtime
```

`Theme` renders `data-fc-theme` on the root wrapper, so two themed regions can coexist.
`Theme::System` renders no attribute and lets `prefers-color-scheme` decide.

The outermost root also mirrors its `data-fc-theme`, `data-fc-brand`, `data-fc-design`
and `data-fc-palette` onto `<html>` after mount, where upstream expects them. A scheme on
the wrapper cannot reach `<html>` or `<body>`, so without the mirror the page canvas
around and beyond the content stays on the OS scheme: a light theme under a dark OS
leaves a dark page behind light components. Nested roots never touch `<html>`.

`<html>` is one element shared by every outermost root, and two roots writing the same
value are indistinguishable there, so ownership lives in one document-side registry
(`core/document-theme.js`) rather than in each root. Each root sends a stable token and
a generation with every update; an update older than the root's last one is dropped,
because each runs as its own script and they can finish out of order. The root that
wrote a name most recently wins it, a root that leaves hands it to the next most recent
owner, and once no root owns it the document gets back the value it had before any root
took it, or none. Hosts without a document keep the theme on the wrapper alone.

## Renderers

Hosts without a stylesheet resource provider can select `Stylesheets::Inline`
on `FutureCss`. This embeds the unchanged generated upstream bundle and disables
component links; it does not add a resource provider or grant network/filesystem
access. Inline CSS delivery alone does not establish renderer layout or keyboard
acceptance. Automatic linked loading remains the default; External keeps loading
under the host's control.

Every renderer Dioxus ships is supported, at least on a best-effort basis: web, desktop,
mobile, server-side rendering with fullstack hydration, liveview, and native (Blitz).
Support is tiered by how much of the platform the renderer provides and how much of it
can be tested automatically, not by which renderers matter more.

| Tier | Renderers | Host | Promise | Checked by |
| --- | --- | --- | --- | --- |
| 1 | Web, SSR and fullstack | A browser | Every component, every state, every behaviour | Full browser suite and SSR parity; release-blocking |
| 2 | Desktop, mobile, liveview | A system webview, or a browser driven over a socket | Same as tier 1; differences are bugs | Demo builds for each in CI; liveview runs the browser suite; desktop runs a smoke suite where a display is available; mobile is checked manually per release |
| 3 | Native (Blitz) | Dioxus's own HTML and CSS engine | Renders and works, with documented fallbacks where the engine lacks a feature | Demo builds in CI; a render smoke test; gaps recorded in the support matrix |

Rules that make this hold:

- **No component calls a renderer-specific API.** Everything host-specific goes through
  `core::platform`, which every renderer implements, even if only by reporting
  `Unsupported`.
- **Every platform call has a fallback.** Overlays render the platform element first,
  so where `showModal` or popovers are unavailable they still open in place (a dialog
  inline with `role="dialog"`, a popover as an in-flow panel) with focus moved and
  returned by Dioxus. A fallback keeps the accessibility contract; it may lose top-layer
  stacking or light dismiss, and says so.
- **Capabilities are detected once, in `FutureCss`,** after mount, and provided through
  context. Render output is identical on every renderer before mount, so SSR and
  hydration agree (see `use_id`).
- **A renderer gap is recorded, not hidden.** `docs/RENDERERS.md` is a support matrix of
  component by renderer, generated from the smoke tests plus manual notes, so a user can
  see which fallback they will get. A gap in a tier 1 or tier 2 renderer is a bug; a gap
  in tier 3 is a fallback until the engine supports the feature, and is reported to
  Dioxus where it is theirs.
- **Files and other host objects** come through a `platform` type with one variant per
  host family (a web `File`, a desktop or mobile path), never a web-only type in a
  public signature.

The demo is the cross-renderer test bed: `cargo xtask demo --renderer <name>` builds and
runs it on any of them.

## Component API conventions

Every component follows these, so the API is guessable from one example.

1. **`#[component]` functions with a `Props` struct**, documented with `///` on every
   field, because rustdoc is the reference and `#![deny(missing_docs)]` enforces it.
2. **Attribute spreading.** Every component takes
   `#[props(extends = GlobalAttributes)] attributes: Vec<Attribute>` (plus the element's
   own attributes where it is a single native element, such as `extends = button`), so a
   consumer can add `id`, `aria-*`, `data-*`, or a class without a new prop. Spread
   attributes are applied before the component's own ARIA, so a consumer cannot
   accidentally clear `role` or `aria-expanded`; consumer `class` is appended, never
   replaces.
   Every list a component spreads is a `Spread`, never a `Vec`: Dioxus diffs a spread
   as a merge of two name-sorted lists but does not sort it, so an unsorted list drops
   the wrong attribute when its membership changes (an icon button that became enabled
   lost its `aria-label`). `Spread::into_boxed_slice`, which rsx calls on every spread,
   sorts; `spread![…]` builds one. `tests/spread.rs` drives the real diff, and the
   architecture lint rejects `..vec!` in components.
3. **Native element first.** A component renders the element the CSS fixture uses:
   `<button>`, `<dialog>`, `<details>`, `<input type=range>`, `<table>`. A `div` with a
   role is used only where the CSS library itself does (the select listbox, the grid).
4. **Events are `EventHandler<T>` with domain types**, not raw DOM events, where the
   component has a domain value: `onchange: EventHandler<String>` on a select,
   `onsort: EventHandler<(usize, SortDirection)>` on a table. Raw events are passed
   through only where the component is a thin native element (`Button::onclick`).
5. **No panics.** Out-of-range input (a selected index past the end, an empty option list,
   an invalid date) renders the documented empty or error state and emits a debug-build
   report.
6. **`Clone + PartialEq` props**, as Dioxus memoization requires. Large data (grid cells,
   diff text, terminal lines) is passed as `ReadSignal<T>` or `Rc<T>` so comparison is
   cheap.
7. **Every state the CSS styles is reachable from a prop**, including loading, error,
   `aria-invalid`, and `aria-busy`. A state only reachable by spreading raw attributes is a
   coverage gap.

## Behaviour: shared keyboard contracts

The TypeScript bindings each implement their keyboard handling. In Rust it is shared:

| Behaviour | Module | Used by |
| --- | --- | --- |
| Roving tabindex, arrows, Home/End, wrap, RTL swap | `behavior::roving` | tabs, toolbar, segmented, button group, list, menu, nav, navbar, datepicker grid, carousel, select list, grid |
| Typeahead | `behavior::typeahead` over `fc-select` / `fc-context-menu` | select, menu, list |
| Escape, light dismiss, focus return | `behavior::dismiss` | dialog, popover, menu, select, split button, FAB menu, search view |
| Polite and assertive announcements, rate limited | `behavior::live` | toast, composer status, agent status, tool call, table sort, grid edit |

`roving` reads `Direction` from context: in RTL, ArrowLeft moves to the *next* item,
because "next" is the reading direction. That rule exists once, so no component can get
it backwards.

## Testing strategy

| Layer | What it proves | Tool |
| --- | --- | --- |
| Unit | class building, enum rendering, behaviour state machines | `cargo test` |
| Markup parity | each component renders the structure its `data-fixture` section uses | `cargo test`, `dioxus-ssr`, structural comparison |
| Accessibility | every rendered fixture passes `fc-a11y` at AA with zero errors | `cargo test` via `fc_dioxus::testing::assert_accessible` |
| Coverage | every class, modifier, and state attribute in the CSS is emitted by some component | `cargo test` (below) |
| Model parity | Rust ports of TypeScript logic agree on every case | upstream's TypeScript at the pinned revision, run under Node, as upstream's `tests/wasm.test.ts` does |
| Browser | keyboard contracts, focus, top-layer behaviour, axe-core | headless Chrome against the demo's fixture page |
| Renderers | every renderer builds the demo; tier 2 and 3 smoke tests | `cargo xtask demo --renderer <name>` |
| Demo | every public component has a showcase entry and a fixture section | `cargo test` (below) |

**Markup parity.** For each `data-fixture` section in upstream's `fixtures.html` there is a Rust
example rendering the same states. The test renders it with `dioxus-ssr` and compares a
structural signature (element names, `fc-` classes, `role`, `aria-*`, `data-fc-*`) with the
fixture's, ignoring text and ids. If the CSS library changes a component's markup, the
Rust test fails, which is the point: the two cannot drift silently.

### Coverage is a test

`tests/coverage.rs` parses every `.fc-*` class and every `[data-fc-*=…]` and
`[aria-*=…]` selector from the synced CSS (the same extraction upstream's linter uses),
renders every component example, and fails listing any class or state value no example
emits, and any `fc-` class an example emits that the CSS does not define. An intentional exclusion (a class used only internally by the CSS, such as
`.fc-term-ansi-*` being produced by the terminal's ANSI parser rather than a prop) is
listed in `coverage-exclusions.toml` with its reason. This is how "full coverage of the
widgets, with all their options" stays true after the CSS library grows.

## The demo

The library ships a demo application, `fc-demo`, in the shape of upstream's demo: a
working page with every component wired up for real, not a gallery of screenshots. The
difference is what it teaches. Upstream's demo shows HTML and JavaScript; this one shows
**the Rust a developer writes**.

It has two pages, mirroring upstream:

- **The showcase.** One section per component, in the order of
  [COMPONENTS.md](COMPONENTS.md). Each section has one or more examples, and each example
  is shown twice: rendered live, and as its Rust source with a copy button. Interactive
  components are interactive. A theme, scheme, and direction switcher applies to the whole
  page, as upstream's does.
- **The fixtures.** Every component in every state the props can express, with no
  interaction needed to reach one, accepting `?dir=rtl` and `?theme=dark` like upstream's
  `fixtures.html`. The parity tests, the accessibility audit, and the browser suite all
  run against this page.

**The snippet is the code that runs.** Each example is one file under
`demo/src/examples/<component>/<example>.rs` containing a single component function. The
demo compiles that file and renders it, and shows the same file's text through
`include_str!`, with a marker comment fencing off the imports it trims for display.
There is no second copy of the snippet to fall out of date: if the shown code would not
compile, the demo does not build. Snippets are highlighted with the library's own
`CodeBlock`, through upstream's `fc-highlight`.

The same example files feed the fixture page and the tests, so writing an example once
gives the showcase entry, the fixture state, the parity check, and the a11y check.

**A component is not complete until it is in the demo.** `tests/demo.rs` lists every
public component in the prelude and fails for any without a showcase section and a
fixture section, the way upstream's bundle test fails a CSS component with no
`data-fixture` section.

The demo runs on every renderer through `cargo xtask demo --renderer <name>`, which is
how tier 2 and 3 renderers are exercised. It is published as a static web build for
each release, so the documentation can link to a live example of every component.

## Versioning and compatibility

- `fc-dioxus` versions independently of future-css but pins the upstream revision it was
  tested against in `upstream.toml`. The vendored assets carry the CSS version, and
  `FutureCss` renders it as `data-fc-version` for diagnosis.
- Dioxus is pinned to one minor version (0.7 at the time of writing). A Dioxus upgrade is
  its own pull request.
- MSRV is the higher of upstream's (`rust-version = "1.82"`) and the pinned Dioxus's;
  the plan's Phase 0 verifies this before any component is written.
